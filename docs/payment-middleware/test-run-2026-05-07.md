# Payment Middleware Local Test Run - 2026-05-07

## Result

The local ngrok test completed the deposit payment path end to end:

1. Beds24 posted a Deposit Payment Request to the local Worker through ngrok.
2. The middleware verified the request against Beds24 API V2.
3. The middleware created a Yoco test checkout.
4. The guest completed a Yoco test card payment.
5. Yoco delivered a `payment.succeeded` webhook.
6. The middleware notified Beds24 through the Custom Gateway notify endpoint.
7. Beds24 accepted the notify with HTTP 200 and an empty response body.
8. The local Payment Request reached `reconciled`.
9. The guest success page observed reconciliation and redirected to the configured Beds24 confirmation URL.

The Beds24 booking-confirmation session survived the Yoco round trip when `BEDS24_CONFIRMATION_URL` was set to the Beds24 confirmation page.

## Integration Findings

- Beds24 Custom Gateway POST data matched the planned contract for Deposit Payment Requests.
- Beds24 posts the deposit amount as `[PAYMENTAMOUNT]`, while the booking invoice item can still represent the full accommodation charge.
- Deposit verification must match the booking-level `deposit` field when the posted amount does not match an invoice item.
- Beds24 API V2 uses the `token` request header. The durable local/prod configuration should use `BEDS24_REFRESH_TOKEN` and mint short-lived access tokens.
- Beds24 Custom Gateway notify URL is `https://api.beds24.com/custompaymentgateway/notify.php`.
- Beds24 notify uses `txnid` for the unique transaction id.
- Beds24 notify success is HTTP 200 with an empty response body. A non-empty body should be treated as an error.
- Yoco webhook signatures are Svix-style: `Webhook-Id`, `Webhook-Timestamp`, and `Webhook-Signature: v1,<base64>`.
- Yoco webhook payload metadata includes `checkoutId`, and the successful payment id is in `payload.id`.
- Behind ngrok, generated Yoco return URLs must honor `X-Forwarded-Proto` and `X-Forwarded-Host` so they use the public HTTPS tunnel origin.

## Balance Payment Request Finding

Booking `86438519` confirmed a second payment through Yoco, but it was not represented locally as a separate Balance Payment Request. The local D1 row for the booking was still the original Deposit Payment Request:

- `payment_type`: `deposit`
- `amount`: `3600.00 ZAR`
- `description`: `Deposit Payment for Newlands Cottages booking 86438519`
- `status`: `reconciled`

Beds24 API also showed one accommodation charge of `7200.00 ZAR` and two paid invoice items of `3600.00 ZAR`, both with the deposit description. This means the second payment was accepted by Beds24 as another deposit-style custom gateway notify, even if the guest entered via a payment request URL.

The likely cause is that the Custom Gateway POST data was still hard-coded as `payment_type=deposit` and `description=Deposit Payment...`. Beds24's `[PAYMENTAMOUNT]` correctly supplied `3600.00`, but the middleware had no distinct signal that the second post was a balance request. The middleware now defensively infers `payment_type=balance` when a same-booking, same-property, same-amount deposit has already completed locally, and it no longer creates another Yoco checkout for an already completed Payment Request.

Recommended Beds24 configuration direction:

- Use the booking confirmation email for the first guest-facing payment/trust copy once the Yoco custom integration is production-ready.
- Add a balance-payment link in the confirmation email once deposit collection has completed or once the booking is confirmed:
  `<a href="https://beds24.com/bookpay.php?bookid=[BOOKID]&g=cg&pay=bookbalance">Pay your remaining balance of [INVOICEBALANCE]</a>`
- Add a reminder Auto Action a configured number of days before arrival with the same `bookpay.php` balance link.
- Keep the Custom Gateway POST data as explicit as possible. If Beds24 allows different Custom Gateway POST data for payment requests, use `payment_type=balance` and a balance description there. If it only allows one global POST template, rely on the middleware's defensive balance inference and validate with capture mode.
- Use `[GUESTLOGIN]` or `https://my-booking.info` as a booking-management link, not as the primary payment link. Guest login shows the booking and payments, but the documented payment-request URL is `bookpay.php?bookid=[BOOKID]`.
